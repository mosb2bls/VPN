## Failures

### F-1: the app cannot open the helper's named pipe — "Access is denied" (all TUN features dead on Windows)
- Steps: install the helper from the app and accept UAC (service runs, pipe exists). Then `get_helper_status`, or `connect` in TUN mode.
- Expected: `running: true` with the helper version; TUN connects.
- Actual: `get_helper_status` → `{installed: true, running: false, version: null}`; `connect` (TUN) → `HELPER_UNREACHABLE`,
  detail **`Access is denied. (os error 5)`**. State stays `disconnected`, networking untouched.
- Evidence (reproduced as the same normal user, outside the app):
  - `NamedPipeClientStream(..., PipeDirection.InOut)` (= `GENERIC_READ | GENERIC_WRITE`) → **"Access to the path is denied."**
  - `NamedPipeClientStream(..., PipeAccessRights 'ReadData, WriteData, ReadAttributes, Synchronize')` → **connects OK**.
- Cause: `crates/winsys/src/pipe.rs:100` `connect()` opens the pipe with
  `std::fs::OpenOptions::new().read(true).write(true)`, i.e. `GENERIC_READ | GENERIC_WRITE`. `GENERIC_WRITE` maps to
  `FILE_GENERIC_WRITE`, which includes `FILE_APPEND_DATA`, `FILE_WRITE_ATTRIBUTES` and `FILE_WRITE_EA`. The pipe DACL
  (`crates/helper/src/server_win.rs:35`) deliberately grants the user only `0x0012008B` (no `FILE_APPEND_DATA`, no write
  attributes / EA), so the open is refused.
- Suggested fix (client side; keep the DACL as is): open with an explicit access mask, e.g.
  `OpenOptionsExt::access_mode(FILE_READ_DATA | FILE_WRITE_DATA | FILE_READ_ATTRIBUTES | SYNCHRONIZE)` (with `access_mode`
  set, `read`/`write` are ignored). Check that nothing later needs `FILE_WRITE_ATTRIBUTES` (e.g. `SetNamedPipeHandleState`
  is not used today — byte mode). A unit / CI test cannot catch this without a real service; please add it to the Windows
  checklist evidence instead.
- Severity: **blocker** (W-TUN, W-DNSLEAK, W-IPV6, W-KILL, W-FORCEKILL 3, W-RESTORE TUN, W-RESTORE-PARTIAL, W-REBOOT TUN, W-INSTALL 4)
- Owner: backend

### F-2: native scrollbars inside the popover while the node picker is open
- Steps: 150 % display scale, two nodes imported, open the popover, click the node row to open the node picker.
- Expected: the picker fits the popover; only the app's own styled scrolling, if any.
- Actual: Windows' native **vertical and horizontal** scrollbars appear on the popover (the page overflows the 340×452 CSS px
  window); they disappear when the picker closes. Not seen on the normal popover.
- Likely cause: the node-picker sheet (or its shadow / transform) is wider / taller than the viewport, and the root has no
  `overflow: hidden`. WebView2 154.
- Severity: minor · Owner: UI

## Checklist issues (docs/TESTING.md §3)
1. **§3.0 `$Repo = "$HOME\VPN"`** — the clone on this PC is `$HOME\Desktop\VPN`. Make it a placeholder ("your clone").
2. **`Loc` cannot detect a bypass when the PC itself exits in GB** (the case here). Add an exit-address comparison
   (`same` / `DIFFERENT` versus a direct baseline, compared by hash) next to `loc=`.
3. **`Loc` / `Invoke-WebRequest` caches the system proxy per PowerShell process**: after one request made while
   disconnected (W-SYSPROXY step 1), later `Loc` calls in the **same window** keep going direct after connecting (observed:
   `exit same` while connected; a fresh `powershell` showed `DIFFERENT`). Run `Loc` in a new process, e.g.
   `powershell -NoProfile -Command "<Loc body>"`, or open a new window after connecting.
4. **`Cn` uses `curl.exe`, which ignores the system proxy** — in system-proxy mode it only proves the direct path. Use
   `Invoke-WebRequest` (fresh process) for the system-proxy checks; keep `curl` for TUN.
5. **SmartScreen**: a file fetched with `gh run download` has no Mark-of-the-Web, so SmartScreen is never consulted. The
   W-INSTALL step should say "download in the browser" (the zip extracted by Explorer keeps `Zone.Identifier`). Even so,
   no warning appeared here — the step's "SmartScreen warns" is not guaranteed.
6. **W-KILL** runs `LocDirect` "in a second elevated window" — that window needs the §3.0 block first.
7. **W-INSTALL step 3**: the uninstaller shows Tauri's "close the running app?" prompt; say whether that is expected
   (the pre-uninstall hook runs `--restore-networking` first). Also mention that the "delete app data" box decides whether
   the node list survives.
8. **W-IPV6 step 4**: also note that IPv6-only sites fail *through* the proxy in system-proxy mode (observed), so the
   expected observation is "IPv6 bypass for apps that ignore the proxy; IPv6-only sites fail for apps that use it".
9. `docs/collab/STATUS.md` (Backend) still says SPEC 1.4.2; SPEC is 1.4.4.
