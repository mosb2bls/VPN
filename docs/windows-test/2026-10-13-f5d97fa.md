## Failures

### F-4: sing-box's Windows Firewall rule stays after Disconnect / Quit (major)
- Steps: TUN connect, then Disconnect (or Quit, or Direct).
- Expected: `Snapshot after before` identical to the pre-connect baseline.
- Actual: `firewallRules DIFFERENT`. A persistent rule remains: display name `sing-tun (C:\Program Files\Lynnk\Helper\sing-box.exe)`,
  **Inbound, Allow, TCP, any local port, any remote address, all profiles (Any)**, local policy store. It is created by
  sing-box's TUN code (sing-tun) on the first TUN connect, reused afterwards (count stays 1), and never removed — also
  not by Disconnect / Quit / Restore networking. Not checked yet whether helper uninstall removes it (W-INSTALL 4 not run).
- Why it matters: priority 3 (exact restore) and it opens inbound TCP to the helper's sing-box binary on every network
  profile, including Public, while Lynnk is not even running.
- Suggested fix: remove the rule in the helper after stopping a TUN session and in `uninstall` (match exactly this display
  name + program path), or stop sing-box from creating it if the TUN inbound needs no inbound allow; add the rule name to
  `net-snapshot.ps1`'s firewall section (it is already caught by the `*sing-box*` pattern).
- Owner: backend

### F-5: after a helper crash the app claims "traffic is blocked" while traffic goes direct, and never reconnects (major)
- Steps: TUN connected, kill switch on; keep the core down (W-KILL loop) and kill `edge-helper` during it.
- Expected (TESTING): the app reconnects (Connected) or ends in Error with a restore report.
- Actual: helper restarted by the SCM after 5.1 s and cleaned up (no `tun0`, no sing-box, 0 WFP filters); traffic went
  **direct** (`exit=same`). The app stayed > 2 min in `degraded`, `lastError ALL_NODES_FAILED` "All configured nodes are
  failing. Traffic is blocked to prevent leaks.", `tunActive: true`, `killSwitchActive: true` — i.e. it told the user they
  were protected / blocked while they were unprotected. No reconnect attempt succeeded. Disconnect → all items `not_needed`;
  Connect → fine.
- Likely cause: the app does not notice that the helper restarted and dropped the session (new helper process / session
  lost) — it keeps treating the old session as alive and the failing probes as "all nodes failing". Suggest: on
  `HELPER_UNREACHABLE` → helper back, query the helper's session state; if there is no session, mark TUN / kill switch
  inactive, report it, and reconnect (or go to Error with a restore report).
- Owner: backend

### F-7: failover return misbehaves after UDP is unblocked (system proxy) (major)
- Steps: block UDP 24443 (rule added before connecting), connect HY2 → switches to REALITY after 54 s; remove the rule.
- Expected: return to HY2 after ~10 min of continuous HY2 success, not before 5 min, no back-and-forth.
- Actual: ~7.8 min after the unblock the active node became **HY2** for ~30 s (sing-box had a UDP socket open — real HY2
  traffic) while `Status.failover` still said "on fallback" with `earliestReturnAt` 2 min later and the popover showed
  "NODE · ON FALLBACK / UK-HY2"; then back to REALITY. After that **no return at all** (still on REALITY 18 min after the
  unblock), although `test_node` on HY2 passed (48 ms, GB) and a fresh connect used HY2 at once.
- Likely cause (to confirm): the running core's HY2 outbound stays broken after a period of blocked UDP, so the background
  primary probe keeps failing; the brief switch suggests the primary probe or a rescue path moves the selector itself.
  Suggest: probe the primary without touching the selector; if the primary keeps failing in the long-running core while a
  fresh test passes, recreate the HY2 outbound / restart the core before deciding.
- Owner: backend

## Checklist issues (docs/TESTING.md §3)
1. W-TUN, W-INSTALL 4, W-REBOOT look for an adapter with `InterfaceDescription -like '*Wintun*'`; on this build it is
   **`tun0` / "sing-tun Tunnel"**. Match `tun0` or `*sing-tun*` as well.
2. **W-FAILOVER**: (a) Windows Firewall does not re-check an already-open UDP flow, so a block rule added after connecting
   never blocks HY2 — add the rule **before** connecting (works in system-proxy mode). (b) In **TUN** mode the rule has no
   effect on the helper's sing-box at all (even before connecting). A different block method is needed for TUN (e.g. block
   UDP 24443 on the router / a phone hotspot, or a WFP filter in a higher-weight sublayer).
3. **W-FAILOVER** expects "a notification about switching" — the app has no OS notifications. Implement or change the step.
4. **W-IPV6 step 3** counts every established IPv6 connection, including ones opened before connecting (7 here, from Edge /
   OneDrive / svchost). Count only connections with `CreationTime` after connecting.
5. **W-DNSLEAK**: `pktmon counters` does not give per-filter, per-adapter counts and pktmon component IDs are hard to map. The
   tester parsed `pktmon etl2txt` and classified packets as TUN (172.19.0.x / fdfe:dcba::) vs physical; consider shipping
   such a script in `scripts/windows/`.
6. **W-KILL**: the suggested "large download" target returned HTTP 403 from `curl`; give a concrete download URL. See F-6.
7. **W-NETCHANGE (b)**: PCs with Modern Standby keep the network up and may wake quickly; say "keep it asleep ≥ 2 min by the
   clock" and check events 506/507 for the actual duration.
8. **W-REBOOT 1** expects a recovery notice; when the helper already cleaned up at boot there is none (O-7).
9. **W-FAILOVER** script / text: after a switch, the return can take > 10 min; the tester's script waits up to 16 min and
   only prints on changes (the owner thought it hung) — say so in the step.
10. **ExitBaseline** becomes stale when the ISP changes the PC's public address (happened overnight): re-run it while
    disconnected after long breaks / reboots, otherwise direct traffic shows as `exit=DIFFERENT`.
